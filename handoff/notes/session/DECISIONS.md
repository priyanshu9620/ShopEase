# Decisions (append-only)

- **D-1 · 2026-11-10 · Scope = resume bullets 2, 3, 4 only.** Bullet 1's features are the user's hand-written college work and stay as they are (bug fixes only if something blocks us). No rewrites of the existing controllers "for cleanliness".
- **D-2 · 2026-11-10 · Keep the stack as-is: Node/Express + Mongoose + React (CRA).** No TypeScript migration, no framework swap. Add only what the bullets need: Redis, Docker, GitHub Actions, Terraform (AWS), S3/CloudFront, socket.io.
- **D-3 · 2026-11-10 · Numbers will be measured, not asserted.** "350 ms → 70 ms, 1,200 RPS" are placeholders. We benchmark before/after Redis with a reproducible load test (k6) against a seeded dataset, record the methodology + results JSON in the repo, and put the measured numbers in the resume even if they differ.
- **D-4 · 2026-11-10 · Infrastructure as code with Terraform, in-repo (`infra/`).** One `terraform apply` builds everything (VPC/SGs, 3 × EC2, ALB + target group + health check, S3 bucket, CloudFront, IAM/OIDC role for GitHub Actions); one `terraform destroy` removes it. Rationale: reproducible, teardown-safe for cost, and a stronger resume/interview story than console clicking.
- **D-5 · 2026-11-10 · "3 replicas" = 3 EC2 instances (not 3 containers on one box).** Each runs the app container; the ALB spreads traffic and health-checks `/healthz`. Instance type: smallest that works (t3.micro / t4g.micro), region `ap-south-1`. Target cost while up ≈ $1–2/day; the stack is up only for build-test-screenshot windows and torn down after.
- **D-6 · 2026-11-10 · Stateful services are NOT on the EC2 fleet.** MongoDB → MongoDB Atlas free tier (M0). Redis → one small managed/hosted instance (Upstash free tier, or Redis on a tiny EC2 if Upstash latency is bad). Rationale: the 3 app replicas must be stateless for the ALB story and for socket.io fan-out.
- **D-7 · 2026-11-10 · CI/CD = GitHub Actions, two workflows.** `ci.yml` on PR: lint, test, build image. `deploy.yml` on push to master: build + push image to GHCR (free) with the commit SHA tag, then roll the 3 instances (SSM Run Command or SSH: `docker pull && docker compose up -d`, one instance at a time, waiting for the ALB health check). AWS auth via **OIDC role** (no long-lived keys in GitHub).
- **D-8 · 2026-11-10 · Redis caching = cache-aside on read endpoints with explicit invalidation.** Endpoints: product list/page/count, single product, category list, search, filters, related, product-category, and product-photo (the heaviest). Keys namespaced + versioned (`shopease:v1:products:page:2`); TTLs; create/update/delete product or category bump a namespace version (no KEYS scans). Measured per-endpoint.
- **D-9 · 2026-11-10 · Static assets = product photos (currently Buffers in Mongo) + the React build.** Phase: upload photos to S3 on create/update (keep Mongo field for backward compat during migration), one-off migration script for existing photos, `photoUrl` served via CloudFront; serve the React build from S3+CloudFront too (ALB only serves `/api`). Rationale: this is what the bullet says and it also makes the EC2 fleet lighter.
- **D-10 · 2026-11-10 · WebSockets = socket.io with the Redis adapter.** Server emits `order:status` to the buyer's room when admin updates status; client subscribes on the orders page and updates live. Redis adapter so an event emitted on replica A reaches a socket on replica B; ALB target group with stickiness for the socket.io handshake. This is the one place bullets 2, 3 and 4 meet — good interview story.
- **D-11 · 2026-11-10 · Load test tool = k6 (scripted, versioned in `bench/`).** Scenarios: browse (list + photos), search, product page; ramp to find max sustainable RPS at p95 < 300 ms. Run locally against docker-compose for before/after Redis; run once against the AWS stack for the "deployed" number. Report both honestly.
- **D-12 · 2026-11-10 · Docs like Pager-Zero.** README (pitch + architecture diagram + measured numbers), `docs/GUIDE.md` (run locally, deploy, teardown, costs), `INTERVIEW_PREP/`. Nothing from any employer anywhere.
- **D-13 · 2026-11-10 · The project is a system-design LAB on the real app, not just three bullets.** `experiments/<nn>-<name>/` — each is one concept (baseline, redis-cache, scale-out, cdn, resilience, zero-downtime deploy, realtime fan-out, aws). `make experiment E=<id>` sets up the environment (docker compose profile / terraform), seeds data idempotently, runs a k6 ramp (step up until p95 > 300 ms or errors > 1 %), collects k6 JSON + Prometheus snapshots (CPU, RPS per replica, cache hit-rate, Mongo ops), writes `report.md` + charts + `results.json`, tears down. Reports are **generated, never hand-written**; the README carries one summary table across experiments. Bullet-3 numbers = 01 vs 02; bullet 4 = 04 + 07; bullet 2 = 03/05/06 locally + 08 on AWS. Caveat stated in every local report: one Mac shares CPU across "replicas"; AWS (08) is where real scale-out is measured.
- **D-14 · 2026-11-10 · Visualization = two free pieces, no custom UI app.** (1) **Live**: Prometheus + Grafana in the compose stack with one *provisioned* dashboard JSON (RPS, p95, errors, per-replica RPS, Redis hit-rate, Mongo ops, CPU); the app exposes `/metrics` via prometheus_client (route, status, replica labels). (2) **Results**: a generated single static `experiments/index.html` (inline SVG charts, no build step — the Pager-Zero approach) published to **GitHub Pages** by CI → permanent public lab URL independent of whether anything is running. Rejected: a bespoke "lab console" runner app (third app to maintain, laptop-only).
- **D-15 · 2026-11-10 · Extensibility contract for new experiments.** An experiment is a folder with `experiment.yml` (title, concept, what-changes-vs-previous, environment profile, k6 scenario + ramp, metrics to snapshot, optional `hooks/{before,during,after}.sh` for chaos such as killing a replica or triggering a deploy). The runner and the report generator are generic and read the manifest; adding a concept (e.g. rate limiting, queue-based writes, read replicas, circuit breaker, connection pooling, sharding) = new folder + maybe a small app change, no runner change. Document this in `experiments/README.md` with a template folder.
- **D-16 · 2026-11-10 · AWS is built with Terraform, not by hand.** The user is already practising manual console setup (VPC/subnets/ALB…) in a separate system-design course, so this project goes straight to infrastructure-as-code: `infra/` (Terraform or OpenTofu) is the only way the stack is created or destroyed. Claude writes and applies it from the terminal with a scoped IAM key the user provides (Claude has no browser). While writing it, every resource block gets a one-line comment on *what it is and why it's needed* so the user can map it to what they learned by hand; the user reviews each `terraform plan` before `apply`. Supersedes the earlier "console first, then Terraform" idea.
- **D-17 · 2026-11-10 · The lab = exactly 10 experiments.** 01 caching (cache-aside, Redis) · 02 scale-out (1→2→3 replicas behind nginx) · 03 fault-tolerance (kill a replica under load) · 04 rolling-deploy (v1→v2 with draining vs naive restart) · 05 db-index (50k products, search before/after indexes) · 06 rate-limit (Redis token bucket, abuser vs normal VUs) · 07 async-queue (BullMQ worker for post-checkout work; the "work" is a Mongo write + 300 ms sleep, no real email/SMS provider) · 08 circuit-breaker (opossum + timeouts/retries around a hanging payment mock) · 09 oversell (200 concurrent buys of 1 unit, read-then-write vs atomic findOneAndUpdate) · 10 cdn-realtime (photos app vs CloudFront; 1,000 sockets across 2 replicas). 01–09 run locally; 02/03/04 get a second run against the AWS stack (the "aws" report). Supersedes the 8-item core list in D-13; EXPERIMENTS-BACKLOG keeps the rest as optional.
- **D-18 · 2026-11-10 · Three ways to see the lab; Docker is the only prerequisite to run it.** (1) Read: generated GitHub Pages site, one page per experiment + a short GIF of Grafana reacting. (2) Run: `make lab` (stack + Prometheus + Grafana), `make experiment E=<id>` for one, `make lab-tour` for all 10 with short ramps; k6, runner and report generator run as containers so a clone needs nothing but Docker; the runner prints "what to watch" + Grafana link before, headline number + report path after; the runner posts Grafana annotations when a hook fires ("replica killed", "index created", "breaker opened"). (3) Show: `make demo E=<id>` 90-second profile + `DEMO.md` per experiment with what to say. Rejected again: a custom web console.
- **D-19 · 2026-11-10 · One provisioned Grafana dashboard for all 10.** Common top row (RPS, p95/p99, error %, RPS per replica) + one collapsed row per concept. All series come from the app's `/metrics` (labels: route, status, replica, origin, client, worker) + redis/mongo exporters; concept-specific gauges (`cache_hit_ratio`, `queue_depth`, `breaker_state`, `stock_level`, `socket_connections`, fan-out histogram, `app_version` state timeline). Dashboard JSON + datasource live in `lab/grafana/` and are mounted into the container (no hand-built dashboards). The report snapshots the same PromQL via Prometheus' API into `results.json` for the static charts.
- **D-20 · 2026-11-10 · AWS/Terraform/ALB/CI/CD plan is unchanged by D-17.** Same phases; Phase 2b grows from 3 local experiments to 9.
- **D-21 · 2026-11-11 · AWS region = `ap-southeast-2` (Sydney), on the user's "new AWS experience" free-plan project ("Rubber Ducking", $100 credits, no charges on the free plan).** The project is region-locked by an organization SCP: EC2/ELB/ECS/Lightsail/S3/CloudFront/ElastiCache/CloudFormation are allowed in Sydney and denied elsewhere (App Runner denied). Supersedes `ap-south-1` in D-5. The IAM user `terraform-shopease` key (pasted in chat by the user, stored as profile `shopease`) is what Terraform uses; rotate it after Phase 3. No budget alert possible/needed on the free plan.
- **D-22 · 2026-11-11 · Data tier fallback: Mongo + Redis on one small "data" EC2 via docker compose until the user creates Atlas.** `MONGO_URL` is a Terraform variable; switching to Atlas later is a one-variable change and a rolling deploy. The 3 app instances stay stateless (D-6 intent preserved).
- **D-23 · 2026-11-11 · Phase 4 shape.** (1) **WebSockets**: socket.io on the same Express server, Redis adapter so an emit on any replica reaches every socket; JWT in the handshake → room `user:<id>`; `order:status` emitted from a middleware on `PUT /order-status/:id` (controller untouched); client `hooks/useOrderUpdates.js` on the Orders page, `transports: ["websocket"]` so no LB stickiness is needed. nginx (lab) gets Upgrade headers; the ALB passes WebSockets natively; CloudFront forwards `/socket.io/*` to the ALB. (2) **Photos on S3 + CloudFront**: `PHOTO_STORAGE=s3` makes a middleware upload the photo buffer after create/update and store `photoUrl` (new optional field); `GET /product-photo/:pid` 302-redirects to the CDN URL when `photoUrl` exists — the client stays unchanged; `scripts/migrate-photos-to-s3.js` moves existing photos. (3) **React build on S3 behind the same CloudFront**; `/api/*` and `/socket.io/*` route to the ALB origin. (4) Experiments renumbered: 10-aws (done), **11-cdn** (photo latency from the laptop via ALB vs CloudFront edge), **12-realtime** (N sockets across replicas, fan-out delivery latency; local lab + AWS). Supersedes the "10 = cdn-realtime" line of D-17.
